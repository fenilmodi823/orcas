## 1. Why this is 7a and not M1.7

The brief's M1.7 bundles six deliverables: the active set, Tier 1 instancing, the LOD
cross-fade, orbit paths, trails, and ground tracks. That is materially larger than M1.6,
which took fifteen tasks and a full session.

There is a clean one-way seam. Paths, trails and ground tracks are all `Line2` work that
*consumes* an active set; the active set, Tier 1 and the cross-fade are what *build* it.
Splitting on that seam gives two roughly M1.6-sized milestones and puts the risky part —
the cross-fade, where drifted constants produce a defect the brief calls "impossible to
un-see" — in front of review before the line work stacks on top of it.

**7a delivers:** dots resolve into oriented shapes as the camera approaches, with no pop,
at bounded cost, and an active set the rest of the subsystem can consume.

**7a explicitly does not deliver:** orbit paths, trails, ground tracks, real 3D models
(P2's asset pipeline is deferred), or the §G.6 CPU saving (see §7).

## 2. What already exists — reuse, do not re-add

Reading the code before designing changed this spec substantially. Three things M1.3
already built are load-bearing here:

| Already in the repo | Consequence for 7a |
| --- | --- |
| `points-attributes.ts` → `PLACEHOLDER_RADIUS_KM = 0.01` with a docstring recording that the ingested `OmmRecord` carries **no `RCS_SIZE` field** — verified against the real CelesTrak OMM schema, not assumed — and citing Rules.md §7 | The "assumed radius" decision was **already made and documented** in M1.3. 7a must import it, never redeclare it. |
| `points-shader-core.ts` computes `float truePx = aRadius * uPixelsPerRadian / dist;` | Apparent pixel size is **already computed on the GPU**, from an existing uniform. The Tier 0 half of the cross-fade is a two-line shader change, not new machinery. |
| `points-shading.ts` → `computePointShading()` mirrors that formula in TypeScript so it is unit-testable without a GPU | The pattern for `lod-band.ts` is established. Extract the shared `truePx` term rather than writing a second copy of it. |

### 2.1 A duplication to fix, not extend

`PLACEHOLDER_RADIUS_KM = 0.01` currently exists **twice**:

- `renderer/points/points-attributes.ts` — the original, fully documented
- `renderer/camera/camera-system.ts` — `TARGET_EXTENTS_RADIUS_KM = 0.01`, with a comment
  that literally reads `// PLACEHOLDER_RADIUS_KM — real per-object sizes are a
  Data-Strategy follow-up`

Adding a third copy for the LOD band is how magic numbers drift apart. 7a moves the single
definition to `renderer/object-extents.ts` and imports it from all three call sites. This
is a deletion, not an addition.

## 3. Architecture

### 3.1 The single band — the one rule that matters

Brief §B.6 and §F.7 both insist on this, so the design makes drift structurally impossible
rather than merely discouraged: **one module owns the band constants, and both tiers read
them from it.**

```text
          3 px                    6 px
           │                       │
Tier 0  ───┴──────╲                │        α = 1 − smoothstep(3, 6, truePx)
                   ╲───────────────┴───
Tier 1  ───────────┬───────╱───────────    α =     smoothstep(3, 6, truePx)
                   │      ╱
```

The invariant is `tier0Alpha(px) + tier1Alpha(px) === 1` for every `px`. Both tiers blend
additively against a black sky, so a constant sum means the eye sees no event at the
crossover. A drifted constant breaks the sum, and the sum is therefore what the test
asserts.

`lod-band.ts` exports the constants once. The GLSL side receives them as two uniforms
(`uLodLoPx`, `uLodHiPx`) pushed from that same module — never as literals in the shader
source.

### 3.2 Rejected approaches

| Approach | Why not |
| --- | --- |
| Per-object alpha computed on the CPU, uploaded to both tiers as an attribute | Doubles per-frame upload and adds a 46k-element JS loop for a value the vertex shader already has every input for. |
| One shader, `discard` above the threshold | No cross-fade is possible at all. This is precisely the pop the milestone exists to remove. |
| Two independently-tuned `smoothstep` calls, one per shader | The exact failure mode §F.7 warns about. |

### 3.3 The active set

Brief §G.6. Two structures, because one cannot serve both consumers cheaply:

- **`Flag` bits in `FrameState.flags`** — what the shader needs, already uploaded per frame.
- **`Uint32Array` of member indices + count** — what CPU consumers need. 7b's trails must
  *iterate* their ≤64 members; scanning 46,250 flags every frame to find them would defeat
  the purpose of having an active set.

```text
ACTIVE SET = selected ∪ hovered ∪ tier-1 members          (7a)
           ∪ pinned ∪ featured ∪ trailed                  (later — no source exists yet)

Cap: 2,048.  Rebuilt in place each frame, zero allocation.
```

`pinned` and `featured` get **no code in 7a**. There is no pin UI and no curated D4 list to
read from; the union shape leaves room, and building empty branches now would be YAGNI.
`featured` becomes real in 7b, where orbit paths need it.

### 3.4 Tier 1 membership

Bounded cost is the whole point of the tier (§B.4), so the cap is enforced at selection
time, not by hoping few objects qualify.

1. Single pass over all N: compute `truePx` per object, collect indices above the band's
   lower edge. Objects failing the visibility filter or flagged `Stale` are skipped.
2. If the candidate count exceeds the cap (2,000), keep the 2,000 largest by `truePx` via
   partial selection — **not** a full sort. At 46k a full sort is ~700k comparisons; a
   quickselect is linear.
3. Rebuild the instance buffers only when membership actually changes.

At the default 42,164 km camera radius essentially nothing exceeds 3 px, so the common case
is an empty candidate list and the cap is never approached. The cap exists for the case
where the camera is deep inside a shell.

**The O(N) scan is affordable because the frame loop is already O(N).** `evaluateFrame`
currently does a `Map` lookup plus a cubic Hermite sample for every object, every frame. A
squared distance is a few flops against that.

### 3.5 Orientation

Fixed nadir-aligned pose from the LVLH frame (§B.4). For a stabilised payload this is
correct; for tumbling debris it is neutral. Inventing a tumble would be dishonest — the
attitude is genuinely unknown, and this is the same reasoning that governs the radius
placeholder.

The octahedron's long axis points at nadir, which is what makes the orientation legible at
4–8 px and gives the tier its purpose over a Tier 0 dot.

`renderer/camera/look-rotation.ts` already has `refUpForObjectLvlh()` (the radial vector).
`lvlh-pose.ts` builds the full quaternion from position and velocity; it reuses the radial
helper rather than recomputing it.

### 4.1 Why `Flag` moves out of `frame-state.ts`

`frame-state.ts` currently declares `Flag` with a single member (`Stale = 1 << 0`). The
brief's §A.3 enum has six, and the active set needs `Selected`/`Hovered` written per frame.
Growing the enum inside `frame-state.ts` would pull selection concerns into the module that
owns the propagation buffers. `simulation/flags.ts` owns the enum; `frame-state.ts`
re-exports it so no existing import breaks.

⚠️ **`Stale`'s numeric value changes** from `1 << 0` to the brief's `1 << 2`. This is a real
breaking change: any consumer comparing raw numbers rather than the enum member would break
silently. The migration task greps every `Flag.` and every raw `flags[` use before touching
the value, and a test asserts `Flag.Stale` round-trips through `evaluateFrame`.

## 5. Data flow

```text
   evaluateFrame  --> FrameState.positions / .velocities / .flags   (O(N), already exists)
                                    |
   camera.position ----------------->|
   viewport height, fov ------------>|
                                    v
                          tier1-select.ts        -- truePx per object, threshold,
                                    |               partial-select to cap 2,000
                                    v
                       tier1Members: Uint32Array
                          |                    |
                          v                    v
             active-set.ts              Tier1Objects.tsx
        (union selected, hovered)   matrices from lvlh-pose,
                 |                  per-instance alpha = tier1Alpha(px)
                 v                             |
        ActiveSet (7b consumes)                |
                                               v
   points-shader-core.ts  alpha = 1 - smoothstep(...) --> sum is 1 across the band
```

Both alpha terms come from `lod-band.ts`. The Tier 0 side reads it as two uniforms; the
Tier 1 side calls `tier1Alpha()` in TypeScript. Same constants, one definition.

## 6. Testing

The brief's M1.7 testing requirements, mapped to what is actually assertable headlessly.

| Brief requirement | How 7a tests it |
| --- | --- |
| "Assert Tier 1 membership never exceeds the cap" | Direct unit test on `selectTier1` with 50,000 synthetic objects all inside the band — asserts `count === cap` and that the kept members are the largest by `truePx`. |
| "Sweep the camera through the crossover band and assert total luminance at the object's pixel varies by < 5%" | The GPU-pixel version needs a GPU. The **invariant underneath it** is `tier0Alpha(px) + tier1Alpha(px) === 1`, and that is what catches drifted constants. Asserted over a fine sweep across and beyond the band, to 1e-12. Plus a live check on `/points`. |
| "Tier 1 cost is bounded and independent of camera position" | `selectTier1` allocates nothing (the same zero-allocation check `frame-state.test.ts` already uses) and its output length is capped regardless of input geometry. |
| "No visible pop at any LOD boundary at any speed" | Subjective — belongs to the live review, not a unit test. Stated as such in the DoD rather than faked with an assertion. |

Additional regression tests this milestone owes:

- **Picking survives the cross-fade.** M1.5's pick pass renders IDs from `aFlags`, not
  colour, so a Tier 0 point faded to alpha 0 is still clickable while its Tier 1 mesh is
  what the user sees. A real behaviour worth pinning, not an assumption.
- **`PLACEHOLDER_RADIUS_KM` has exactly one definition.** A source-grepping test would be
  brittle; instead `camera-system.ts` and `lod-band.ts` import the constant and a test
  asserts all three uses are referentially the same value.
- **`Flag.Stale` round-trips** through `evaluateFrame` after the enum renumbering.

## 7. What 7a deliberately does not do

Stated so a later reader does not mistake absence for oversight.

- **No real 3D models.** Tier 2 (§B.5) needs glTF/meshopt/KTX2 and licensed assets — P2's
  asset pipeline, explicitly deferred. Every Tier 1 object is the same octahedron proxy.
- **No per-object sizes.** The ingested OMM has no `RCS_SIZE`. Every object keeps M1.3's
  one documented 10 m placeholder. When real sizes land, `packRadii` becomes a lookup and
  neither the px formula nor the band changes.
- **No §G.6 CPU saving yet.** The active set is *built* here; the payoff — restricting CPU
  Hermite to its members — is M1.8's GPU-Hermite work. `evaluateFrame` still evaluates all
  N. Saying otherwise would overstate the milestone.
- **No `PerformanceMonitor` tier ladder.** That is M1.8 (Part 11.2).
- **The pick `suppressed` flag stays unwired.** Carried from M1.5, still always `false`. It
  belongs with 7b's active-set work or with M1.8, not here.
